## A. 代码级采用（MIT，可 vendor）

### A1. step-up 令牌（护士确认 / 授权撤回凭证）

- 来源：`r6/stepup.py`（约 300 行），依赖 `r6/constant_time.py`、`r6/runtime_config.py`，可选 Redis。
- 保留：HMAC-SHA256 签名格式 `{base64url_payload}.{hmac_hex_signature}`；scope 白名单（frozenset，拒绝 denylist 思路）；nonce 防重放；默认 TTL 300 s。
- 必改：
  1. 签名载荷加入 `record_digest + nurse_id + action_id`（原版只绑 tenant/scope）；
  2. nonce 存储从"Redis 或进程内存"改为**数据库表**（原版注释明确：无 Redis 时单进程内存不满足生产，见其 #212）——本项目院内单机部署无 Redis；
  3. 删除 `PATIENT_CONNECT_SUBJECT`、`READ_TOKEN_TTL_SECONDS` 等患者连接令牌逻辑。

```python
# 原版要点（r6/stepup.py）—— 保留部分
DEFAULT_TOKEN_TTL_SECONDS = 300

# scope 用白名单而非黑名单：新增 scope 必须显式决策并配测试
WRITE_SCOPES = frozenset({None, 'write'})
READ_SCOPES = WRITE_SCOPES | {'read'}

# nonce 防重放：首次消费记录 nonce，同 nonce 再次校验即拒绝
def mark_nonce_used(nonce, exp):
    """Record a nonce as consumed until `exp`.
    Returns: True if newly recorded, False if replay."""
    if not nonce:
        return True          # 无 nonce 视为首次使用
    ...  # 原版走 Redis(SET NX EX) 或进程内 dict —— 必改为数据库实现
```

- 验收：SEC-02（过期令牌拒绝）、SEC-03（同一令牌二次确认拒绝）。

### A2. fail-closed 审计写入

- 来源：`r6/audit.py`。保留核心语义：**审计写不进去，业务就一起回滚**。这是"留痕可信"的地基，也是原版 `issue #182`（吞掉审计失败导致 201 但什么都没存）的教训。
- 必改：原版耦合 Flask-SQLAlchemy 的 `models.db` 会话与 `r6.health_context`；改为接收本项目 `Session` 参数，去掉 Flask 依赖。保留"agent_id 不合规时降级为键控哈希"的做法（防止把令牌贴进 `X-Agent-Id` 头落库）。

```python
# 原版要点（r6/audit.py）—— 语义保留，会话改为注入
class AuditWriteError(RuntimeError):
    """Raised when a mandatory AuditEvent could not be written.
    ... an access that cannot be audited must fail loudly rather
    than proceed unrecorded."""

def add_audit_event(db, event_type, resource_id=None, agent_id=None,
                    outcome='success', detail=None, tenant_id=None):
    """在调用方事务内写入并 flush：
    审计与业务状态变更同生共死（调用方 commit 前调用）。"""
    audit = AuditEventRecord(event_type=event_type, resource_id=resource_id,
                             agent_id=_storable_agent_id(agent_id),
                             outcome=outcome, detail=detail, tenant_id=tenant_id)
    db.add(audit)
    db.flush()          # flush 失败 → 整个事务回滚，业务不落库
    return audit
```

- 事件类型扩为本项目三类：操作 / 升级 / 授权（对应 REQ-05 与医疗-015）。
- 验收：SEC-05（审计表人为注入失败 → 业务写入必须整体失败）。

### A3. append-only 触发器（DB 层拒绝 UPDATE/DELETE）

- 来源：`r6/audit_ddl.py`。Postgres 用函数 + BEFORE UPDATE OR DELETE 触发器，SQLite 用同语义触发器；DDL 幂等。
- 必改：① 补 `prev_hash`/`entry_hash` 两列与链校验脚本（原版明确"这不是账本"，见其文件头）；② 保留原版三条自述限制进运维文档：TRUNCATE 不触发、表 owner 可禁用触发器、SQLite `batch_alter_table` 重建表会丢触发器（迁移后必须重跑 `install_statements`）。

```sql
-- 原版要点（r6/audit_ddl.py，Postgres 部分）—— 原样采用
CREATE OR REPLACE FUNCTION audit_events_append_only() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    RAISE EXCEPTION USING
        MESSAGE = 'audit_events is append-only, ' || TG_OP || ' refused';
END;
$$;

CREATE TRIGGER audit_events_append_only
BEFORE UPDATE OR DELETE ON audit_events
FOR EACH ROW EXECUTE FUNCTION audit_events_append_only();
```

```python
# 配套自写：哈希链补强（原版没有，必须加）
def entry_hash(secret: bytes, prev_hash: str, payload: dict) -> str:
    canonical = json.dumps(payload, sort_keys=True, ensure_ascii=False,
                           separators=(',', ':'))
    return hmac.new(secret, f"{prev_hash}|{canonical}".encode(),
                    hashlib.sha256).hexdigest()
# 每行 audit_events 写入时带 prev_hash/entry_hash；日结脚本重放全链校验，
# 另存当日 digest 到只读备份库。
```

- 验收：SEC-05（UPDATE/DELETE 直接被触发器拒绝；篡改任意一行 → 链校验失败）。

### A4. 日志卫生（键控哈希，不写调用方原文）

- 来源：`r6/log_safety.py`。纯标准库、耦合最低，**基本原样 vendor**。核心思想：调用方可任填 `X-Tenant-Id`/`X-Agent-Id`，凭形状识别令牌不可靠，所以日志**永远不写调用方 ID 原文**，只写短键控哈希（10 位 hex，前缀 `t:`），拥有 secret 的人可反算检索。query string 一律不记。
- 必改：把 `_KEY_LABEL` 域分隔标签改为本项目名（`fde-followup-log-id-v1`）；正则保留（覆盖 JWT、OpenAI/Anthropic key、GitHub token、Slack token、AWS AKIA、bearer）。

```python
# 原版要点（r6/log_safety.py）
_CREDENTIAL_SHAPED = re.compile(
    r'eyJ[A-Za-z0-9_=-]{8,}(?:\.[A-Za-z0-9_=.-]*)?'          # JWT
    r'|(?<![A-Za-z0-9])(?:sk|rk|pk)[-][A-Za-z0-9_-]{16,}'    # 平台 key
    r'|...xox[abprs]-...|AKIA[0-9A-Z]{16}|bearer\s+\S+'
)

def _key() -> bytes | None:
    secret = os.environ.get('STEP_UP_SECRET', '')
    # 域分隔：从 step-up secret 派生日志专用 key，防止用日志反推签名
    return hmac.new(secret.encode(), _KEY_LABEL, hashlib.sha256).digest()
```

- 验收：SEC-09（把住院号/手机号塞进请求头，日志里只出现键控哈希）。

### A5. 请求体深度/大小防护

- 来源：`r6/body_guard.py`。保留"有界深度检查"实现（在到达 Python 递归上限之前拒绝 ~1000 层嵌套载荷，且检查器自身不超过 limit+1 层）。

```python
# 原版要点（r6/body_guard.py）
INGEST_MAX_JSON_DEPTH = 32

def json_depth_within(obj, limit, _depth=0):
    if _depth > limit:                 # 拒绝点在 32，不碰递归上限
        return False
    if isinstance(obj, dict):
        return all(json_depth_within(v, limit, _depth + 1) for v in obj.values())
    if isinstance(obj, list):
        return all(json_depth_within(v, limit, _depth + 1) for v in obj)
    return True
```

- 必改：只依赖 `flask.request`，改成接收已解析的 dict/list 即可脱离 Flask；保留"auth 门之前先做深度检查"的调用顺序（原版 #312：解析在鉴权前，几 KB 的 `[[[[...` 就能打出 500）。
- 验收：SEC-11（深嵌套与超大载荷返回 4xx 且不产生堆栈日志）。
